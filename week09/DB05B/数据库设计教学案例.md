## 一、需求分析

### 1.1 项目背景

某高校每年举办全校田径运动会，需要开发一个数据库系统来管理运动会相关信息。通过本项目，学习数据库系统设计的完整流程。

### 1.2 功能需求

| 编号 | 需求类别 | 具体描述 |
|------|----------|----------|
| R1 | 运动会管理 | 每届运动会具有届次编号、名称、举办日期、举办地点 |
| R2 | 竞赛项目管理 | 每个竞赛项目具有项目编号、项目名称、项目类别、是否团体项目 |
| R3 | 裁判管理 | 每位裁判具有裁判编号、姓名、裁判等级；裁判可在多个项目中担任不同职务 |
| R4 | 运动员管理 | 每位运动员具有运动员编号、姓名、性别、所属学院，可拥有多个联系电话 |
| R5 | 参赛管理 | 运动员报名参加竞赛项目，记录参赛成绩、名次、是否破纪录 |
| R6 | 执裁管理 | 裁判与竞赛项目的执裁关系，记录具体职务 |
| R7 | 成绩统计 | 查询项目成绩排名、破纪录情况、运动员参赛统计 |

### 1.3 数据需求

#### 1.3.1 数据项说明

| 数据项 | 说明 | 数据类型 | 取值范围/约束 |
|--------|------|----------|---------------|
| 届次编号 | 运动会唯一标识 | 字符串 | 如 M2024, M2025 |
| 项目名称 | 竞赛项目唯一名称 | 字符串 | 如"男子100米" |
| 项目类别 | 竞赛项目的类型 | 枚举 | 田赛/径赛/团体 |
| 裁判等级 | 裁判的资质等级 | 枚举 | 国家级/一级/二级 |
| 联系电话 | 运动员的联系方式 | 字符串 | 多值属性 |
| 成绩 | 参赛成绩 | 数值 | 如 10.5（秒）、5.68（米） |
| 是否破纪录 | 成绩是否打破纪录 | 布尔值 | True / False |

#### 1.3.2 处理需求

| 处理 | 输入 | 输出 | 说明 |
|------|------|------|------|
| 添加运动会 | 届次、名称、日期、地点 | 成功/失败 | 届次和名称唯一 |
| 运动员报名 | 运动员编号、项目编号 | 成功/失败 | 同一运动员可报多个项目 |
| 成绩录入 | 运动员编号、项目编号、成绩、名次 | 成功/失败 | 成绩可空（未比赛） |
| 项目排名查询 | 项目编号 | 按成绩排序的运动员列表 | 径赛成绩越小越好，田赛成绩越大越好 |
| 破纪录查询 | 无 | 所有破纪录的参赛记录 | 显示运动员、项目、成绩 |

### 1.4 需求分析小结

通过需求分析，我们明确了系统中涉及的**四类核心实体**：运动会、竞赛项目、裁判、运动员，以及**两个多对多关系**：裁判执裁项目、运动员参加项目。此外，运动员的联系电话是**多值属性**，需要特殊处理。

## 二、概念结构设计

### 2.1 设计目标

将需求分析阶段识别的数据对象抽象为**实体（Entity）**和**联系（Relationship）**，使用 ER（Entity-Relationship）模型进行概念建模。

### 2.2 实体识别

| 实体 | 定义 | 候选键 |
|------|------|--------|
| 运动会 (SportsMeet) | 每届全校田径运动会 | 届次编号（唯一） |
| 竞赛项目 (Event) | 运动会中的具体比赛项目 | 项目编号（唯一） |
| 裁判 (Referee) | 执裁竞赛项目的工作人员 | 裁判编号（唯一） |
| 运动员 (Athlete) | 参加竞赛项目的学生 | 运动员编号（唯一） |

### 2.3 实体属性分析

#### 2.3.1 运动会 (SportsMeet)

| 属性 | 英文名 | 数据类型 | 是否主键 | 是否唯一 | 是否非空 | 说明 |
|------|--------|----------|----------|----------|----------|------|
| 届次编号 | meet_id | VARCHAR(20) | 是 | 是 | 是 | 唯一标识 |
| 名称 | name | VARCHAR(100) | 否 | 是 | 是 | 如"第46届田径运动会" |
| 举办日期 | meet_date | DATE | 否 | 否 | 是 | 运动会举办日期 |
| 举办地点 | location | VARCHAR(200) | 否 | 否 | 否 | 运动会举办地点 |

#### 2.3.2 竞赛项目 (Event)

| 属性 | 英文名 | 数据类型 | 是否主键 | 是否唯一 | 是否非空 | 说明 |
|------|--------|----------|----------|----------|----------|------|
| 项目编号 | event_id | VARCHAR(20) | 是 | 是 | 是 | 唯一标识 |
| 项目名称 | event_name | VARCHAR(100) | 否 | 是 | 是 | 如"男子100米" |
| 项目类别 | category | ENUM | 否 | 否 | 是 | 田赛/径赛/团体 |
| 是否团体项目 | is_team | BOOLEAN | 否 | 否 | 是 | True/False |
| 届次编号 | meet_id | VARCHAR(20) | 否 | 否 | 是 | 外键，关联运动会 |

#### 2.3.3 裁判 (Referee)

| 属性 | 英文名 | 数据类型 | 是否主键 | 是否唯一 | 是否非空 | 说明 |
|------|--------|----------|----------|----------|----------|------|
| 裁判编号 | referee_id | VARCHAR(20) | 是 | 是 | 是 | 唯一标识 |
| 姓名 | name | VARCHAR(50) | 否 | 否 | 是 | 裁判姓名 |
| 裁判等级 | level | VARCHAR(20) | 否 | 否 | 是 | 国家级/一级/二级 |

#### 2.3.4 运动员 (Athlete)

| 属性 | 英文名 | 数据类型 | 是否主键 | 是否唯一 | 是否非空 | 说明 |
|------|--------|----------|----------|----------|----------|------|
| 运动员编号 | athlete_id | VARCHAR(20) | 是 | 是 | 是 | 唯一标识 |
| 姓名 | name | VARCHAR(50) | 否 | 否 | 是 | 运动员姓名 |
| 性别 | gender | ENUM | 否 | 否 | 是 | 男/女 |
| 所属学院 | college | VARCHAR(100) | 否 | 否 | 是 | 如"计算机学院" |

> **注意**：运动员的"联系电话"是**多值属性**（一个运动员可以有多个电话），在 ER 建模中应使用**双椭圆**表示。在关系模型中需要单独建表处理。

### 2.4 联系识别

#### 2.4.1 包含（运动会 —— 竞赛项目）

| 项目 | 说明 |
|------|------|
| 联系名 | 包含 (Contains) |
| 参与实体 | 运动会、竞赛项目 |
| 基数 | 1 : N（一对多） |
| 语义 | 每届运动会包含多个竞赛项目，每个竞赛项目属于且仅属于一届运动会 |
| 联系属性 | 无 |

#### 2.4.2 执裁（裁判 —— 竞赛项目）

| 项目 | 说明 |
|------|------|
| 联系名 | 执裁 (Referees) |
| 参与实体 | 裁判、竞赛项目 |
| 基数 | M : N（多对多） |
| 语义 | 一名裁判可执裁多个竞赛项目，一个竞赛项目可由多名裁判共同执裁 |
| 联系属性 | 职务（如"主裁判"、"计时裁判"） |

> **关键点**："职务"是依赖于具体的（裁判，项目）组合的属性。同一裁判在不同项目中可能担任不同职务，因此职务不能作为裁判或项目的独立属性，必须作为联系的属性。

#### 2.4.3 参加（运动员 —— 竞赛项目）

| 项目 | 说明 |
|------|------|
| 联系名 | 参加 (Participates) |
| 参与实体 | 运动员、竞赛项目 |
| 基数 | M : N（多对多） |
| 语义 | 一名运动员可参加多个竞赛项目，一个竞赛项目有多名运动员参加 |
| 联系属性 | 成绩、名次、是否破纪录 |

> **关键点**："成绩"是运动员参加某个项目后才产生的数据，既不是运动员的固有属性，也不是项目的固有属性。因此成绩必须建模为**参加**联系的属性。

### 2.6 常见错误分析（教学要点）

| 错误做法 | 正确做法 | 原因分析 |
|----------|----------|----------|
| 将"成绩"作为运动员的属性 | 成绩作为"参加"联系的属性 | 成绩依赖于（运动员，项目）的组合，单独放在任何一方都不完整 |
| 将"职务"作为裁判的属性 | 职务作为"执裁"联系的属性 | 同一裁判在不同项目中职务可能不同 |
| 将联系电话作为运动员的单值属性 | 多值属性，单独建表 | 一个运动员可以有多个联系电话 |
| 为"竞赛成绩"创建独立实体 | 成绩是联系的属性，无需独立实体 | 避免过度设计，简化模型 |
| 在裁判和运动员之间建立联系 | 两者没有直接联系 | 需求明确说明裁判与运动员没有直接关联 |

## 三、逻辑结构设计

### 3.1 ER 图向关系模式的转换规则

#### 规则 1：实体 → 关系模式
每个实体直接转换为一个关系（表），实体的属性成为表的列，候选键成为主键。

#### 规则 2：1:N 联系 → 外键
将 1 端实体的主键作为 N 端的外键。例如"运动会—竞赛项目"的 1:N 联系，在竞赛项目表中添加 `meet_id` 外键。

#### 规则 3：M:N 联系 → 独立关系模式
将 M:N 联系转换为一个独立的关系（表），包含两端实体的主键作为联合主键，联系的属性也作为表的列。

#### 规则 4：多值属性 → 独立关系模式
将多值属性转换为一个独立的关系（表），包含所属实体的主键作为外键，多值属性本身作为联合主键的一部分。

### 3.2 关系模式设计

#### 3.2.1 运动会表（sports_meet）

```
sports_meet(
    meet_id     VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(100) NOT NULL UNIQUE,
    meet_date   DATE NOT NULL,
    location    VARCHAR(200)
)
```

#### 3.2.2 竞赛项目表（event）

```
event(
    event_id        VARCHAR(20) PRIMARY KEY,
    event_name      VARCHAR(100) NOT NULL UNIQUE,
    category        ENUM('田赛', '径赛', '团体') NOT NULL,
    is_team         BOOLEAN NOT NULL DEFAULT FALSE,
    meet_id         VARCHAR(20) NOT NULL,
    FOREIGN KEY (meet_id) REFERENCES sports_meet(meet_id)
        ON DELETE CASCADE
)
```

> 说明：`meet_id` 是外键，实现运动会与竞赛项目的 1:N 联系。`ON DELETE CASCADE` 表示删除运动会时，其包含的竞赛项目也自动删除。

#### 3.2.3 裁判表（referee）

```
referee(
    referee_id  VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,
    level       VARCHAR(20) NOT NULL
)
```

#### 3.2.4 运动员表（athlete）

```
athlete(
    athlete_id  VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,
    gender      ENUM('男', '女') NOT NULL,
    college     VARCHAR(100) NOT NULL
)
```

#### 3.2.5 运动员联系电话表（athlete_phone）

```
athlete_phone(
    athlete_id  VARCHAR(20) NOT NULL,
    phone       VARCHAR(20) NOT NULL,
    PRIMARY KEY (athlete_id, phone),
    FOREIGN KEY (athlete_id) REFERENCES athlete(athlete_id)
        ON DELETE CASCADE
)
```

> 说明：这是多值属性"联系电话"的独立关系模式。联合主键 `(athlete_id, phone)` 确保同一电话不会重复添加到同一运动员。

#### 3.2.6 执裁关系表（referee_event）

```
referee_event(
    referee_id  VARCHAR(20) NOT NULL,
    event_id    VARCHAR(20) NOT NULL,
    role        VARCHAR(50) NOT NULL,
    PRIMARY KEY (referee_id, event_id),
    FOREIGN KEY (referee_id) REFERENCES referee(referee_id)
        ON DELETE CASCADE,
    FOREIGN KEY (event_id) REFERENCES event(event_id)
        ON DELETE CASCADE
)
```

> 说明：这是"执裁"M:N 联系的独立关系模式。`role`（职务）是联系的属性。`ON DELETE CASCADE` 表示删除裁判或项目时，相关的执裁记录自动删除。

#### 3.2.7 参赛关系表（participation）

```
participation(
    athlete_id  VARCHAR(20) NOT NULL,
    event_id    VARCHAR(20) NOT NULL,
    score       DECIMAL(10,2) DEFAULT NULL,
    rank_num    INT DEFAULT NULL,
    is_record   BOOLEAN DEFAULT FALSE,
    PRIMARY KEY (athlete_id, event_id),
    FOREIGN KEY (athlete_id) REFERENCES athlete(athlete_id)
        ON DELETE CASCADE,
    FOREIGN KEY (event_id) REFERENCES event(event_id)
        ON DELETE CASCADE
)
```

> 说明：这是"参加"M:N 联系的独立关系模式。`score`、`rank_num`、`is_record` 是联系的属性。成绩和名次允许为空（报名后未比赛时）。

### 3.3 关系模式汇总

| 关系（表） | 主键 | 外键 | 说明 |
|-----------|------|------|------|
| sports_meet | meet_id | 无 | 运动会信息 |
| event | event_id | meet_id → sports_meet | 竞赛项目信息 |
| referee | referee_id | 无 | 裁判信息 |
| athlete | athlete_id | 无 | 运动员信息 |
| athlete_phone | (athlete_id, phone) | athlete_id → athlete | 多值属性：联系电话 |
| referee_event | (referee_id, event_id) | referee_id → referee, event_id → event | M:N 联系：执裁 |
| participation | (athlete_id, event_id) | athlete_id → athlete, event_id → event | M:N 联系：参加 |

## 四、物理结构设计

### 4.1 存储结构与存取方法

#### 4.1.1 数据库配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 数据库引擎 | InnoDB | 支持事务、外键、行级锁 |
| 字符集 | utf8mb4 | 支持完整的 Unicode 字符（含中文、emoji） |
| 排序规则 | utf8mb4_unicode_ci | Unicode 排序，不区分大小写 |

#### 4.1.2 索引设计

主键自动创建聚簇索引。以下是额外需要创建的索引：

| 表名 | 索引字段 | 索引类型 | 说明 |
|------|----------|----------|------|
| event | meet_id | 普通索引 | 加速按运动会查询项目 |
| event | event_name | 唯一索引 | 项目名称唯一约束（已包含） |
| athlete_phone | athlete_id | 普通索引 | 加速按运动员查询电话 |
| referee_event | event_id | 普通索引 | 加速按项目查询裁判 |
| participation | event_id | 普通索引 | 加速按项目查询参赛运动员 |
| participation | score | 普通索引 | 加速按成绩排序和排名查询 |

#### 4.1.3 完整性约束

| 约束类型 | 实现位置 | 说明 |
|----------|----------|------|
| 实体完整性 | 所有表的主键 | 确保每行记录唯一 |
| 参照完整性 | 所有外键约束 | 确保关联数据的一致性 |
| 用户定义完整性 | category ENUM | 限制项目类别只能取指定值 |
| 用户定义完整性 | gender ENUM | 限制性别只能取指定值 |
| 用户定义完整性 | UNIQUE(name) | sports_meet 的名称唯一 |
| 用户定义完整性 | UNIQUE(event_name) | event 的项目名称唯一 |

### 4.2 完整建表 SQL

```sql
-- 创建数据库
CREATE DATABASE IF NOT EXISTS sports_meet_db
    DEFAULT CHARSET=utf8mb4
    COLLATE=utf8mb4_unicode_ci;

USE sports_meet_db;

-- 运动会表
CREATE TABLE IF NOT EXISTS sports_meet (
    meet_id     VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(100) NOT NULL UNIQUE,
    meet_date   DATE NOT NULL,
    location    VARCHAR(200),
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 竞赛项目表
CREATE TABLE IF NOT EXISTS event (
    event_id        VARCHAR(20) PRIMARY KEY,
    event_name      VARCHAR(100) NOT NULL UNIQUE,
    category        ENUM('田赛', '径赛', '团体') NOT NULL,
    is_team         BOOLEAN NOT NULL DEFAULT FALSE,
    meet_id         VARCHAR(20) NOT NULL,
    CONSTRAINT fk_event_meet
        FOREIGN KEY (meet_id) REFERENCES sports_meet(meet_id)
        ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 裁判表
CREATE TABLE IF NOT EXISTS referee (
    referee_id  VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,
    level       VARCHAR(20) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 运动员表
CREATE TABLE IF NOT EXISTS athlete (
    athlete_id  VARCHAR(20) PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,
    gender      ENUM('男', '女') NOT NULL,
    college     VARCHAR(100) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 运动员联系电话表（多值属性）
CREATE TABLE IF NOT EXISTS athlete_phone (
    athlete_id  VARCHAR(20) NOT NULL,
    phone       VARCHAR(20) NOT NULL,
    PRIMARY KEY (athlete_id, phone),
    CONSTRAINT fk_phone_athlete
        FOREIGN KEY (athlete_id) REFERENCES athlete(athlete_id)
        ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 执裁关系表（裁判-竞赛项目 M:N，联系属性：职务）
CREATE TABLE IF NOT EXISTS referee_event (
    referee_id  VARCHAR(20) NOT NULL,
    event_id    VARCHAR(20) NOT NULL,
    role        VARCHAR(50) NOT NULL,
    PRIMARY KEY (referee_id, event_id),
    CONSTRAINT fk_re_referee
        FOREIGN KEY (referee_id) REFERENCES referee(referee_id)
        ON DELETE CASCADE,
    CONSTRAINT fk_re_event
        FOREIGN KEY (event_id) REFERENCES event(event_id)
        ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 参赛关系表（运动员-竞赛项目 M:N，联系属性：成绩、名次、是否破纪录）
CREATE TABLE IF NOT EXISTS participation (
    athlete_id  VARCHAR(20) NOT NULL,
    event_id    VARCHAR(20) NOT NULL,
    score       DECIMAL(10,2) DEFAULT NULL,
    rank_num    INT DEFAULT NULL,
    is_record   BOOLEAN DEFAULT FALSE,
    PRIMARY KEY (athlete_id, event_id),
    CONSTRAINT fk_pa_athlete
        FOREIGN KEY (athlete_id) REFERENCES athlete(athlete_id)
        ON DELETE CASCADE,
    CONSTRAINT fk_pa_event
        FOREIGN KEY (event_id) REFERENCES event(event_id)
        ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

```python
import mysql.connector
from mysql.connector import Error

class Database:
    def __init__(self, host, database, user, password):
        self.connection_config = {
            'host': host, 'database': database,
            'user': user, 'password': password,
            'charset': 'utf8mb4', 'collation': 'utf8mb4_unicode_ci'
        }
        self.connection = None
        self.cursor = None

    def connect(self):
        try:
            self.connection = mysql.connector.connect(**self.connection_config)
            self.cursor = self.connection.cursor(dictionary=True)
            return True
        except Error as e:
            print(f"数据库连接失败：{e}")
            return False
```

## 七、常见问题与解答

### Q1：为什么成绩不能作为运动员的属性？

**答**：成绩是运动员参加某个具体项目后才产生的数据，它依赖于（运动员，项目）这个组合。如果作为运动员的属性，一个运动员有多个成绩就无法表示；如果作为项目的属性，一个项目有多个运动员的成绩也无法表示。因此成绩必须是**参加**联系的属性。

### Q2：为什么联系电话要单独建表？

**答**：联系电话是**多值属性**（Multivalued Attribute），即一个运动员可以有多个联系电话。在关系模型中，一个属性列只能存储一个值，因此需要将多值属性拆分为独立的表，通过外键关联。

### Q3：执裁关系和参加关系都用中间表，它们有什么区别？

**答**：两者都是 M:N 联系的实现方式，但联系属性不同：
- **执裁关系**的中间表 `referee_event` 有属性 `role`（职务）
- **参赛关系**的中间表 `participation` 有属性 `score`（成绩）、`rank_num`（名次）、`is_record`（是否破纪录）

不同的 M:N 联系有不同的业务含义，因此需要分别建立独立的中间表。

### Q4：外键删除策略为什么选择 CASCADE？

**答**：`CASCADE`（级联删除）确保数据一致性。例如删除一名裁判后，他在各个项目中的执裁记录已经没有意义，应该自动清除。如果选择 `RESTRICT`，删除裁判时会因为存在关联记录而失败，需要手动先删除所有执裁记录，操作繁琐且容易遗漏。

### Q5：ENUM 类型和 VARCHAR 有什么区别？

**答**：`ENUM` 是枚举类型，只能取预定义的值，如 `ENUM('男', '女')`。优点是数据库会自动校验输入值是否合法，保证数据质量。`VARCHAR` 可以存储任意字符串，灵活性高但缺乏约束。在本系统中，性别、项目类别等取值范围固定的字段使用 `ENUM`，地点、学院等取值自由的字段使用 `VARCHAR`。
