# 《DB作业07B：关系数据库规范化设计理论》讲解用简单案例

> 用途：这些案例用于课堂讲解、启发学生理解题意。  
> 建议使用方式：先讲“生活化小例子”，再回到作业中的正式关系模式。  
> 核心主线：函数依赖 → 候选键 → 范式判断 → 分解 → 无损连接 → 保持依赖。

---

# 一、简答题讲解案例

## 1. 什么是有损分解？“寄生元组”如何产生？

### 简单案例

原来有一张表：

| 学生 | 课程 | 教师 |
|---|---|---|
| 小明 | 数据库 | 王老师 |
| 小红 | 数据库 | 王老师 |

如果错误地拆成两张表：

**表1：学生-课程**

| 学生 | 课程 |
|---|---|
| 小明 | 数据库 |
| 小红 | 数据库 |

**表2：课程-教师**

| 课程 | 教师 |
|---|---|
| 数据库 | 王老师 |

再连接回来时，目前还没有问题。

但是如果表2中还有：

| 课程 | 教师 |
|---|---|
| 数据库 | 王老师 |
| 数据库 | 李老师 |

连接回来就会得到：

| 学生 | 课程 | 教师 |
|---|---|---|
| 小明 | 数据库 | 王老师 |
| 小明 | 数据库 | 李老师 |
| 小红 | 数据库 | 王老师 |
| 小红 | 数据库 | 李老师 |

其中“小明-数据库-李老师”“小红-数据库-李老师”可能原来根本不存在，这就是**寄生元组**。

### 提示

有损分解不是说数据丢了，而是说**重新连接后出现了原来没有的数据**。  
也可以理解为：拆表时丢失了某些约束关系，导致连接时“乱配对”。

---

## 2. 2NF 和 3NF 在消除依赖类型上有什么区别？

### 简单案例：2NF 关注“部分依赖”

原表：

| 学号 | 课程号 | 学生姓名 | 课程名 | 成绩 |
|---|---|---|---|---|
| S01 | C01 | 小明 | 数据库 | 90 |

候选键是：

```text
(学号, 课程号)
```

因为一个学生一门课才有一个成绩。

但是：

```text
学号 → 学生姓名
课程号 → 课程名
```

这里“学号”和“课程号”都是复合键的一部分，却能决定非主属性。  
这叫**部分依赖**，所以不满足 2NF。

### 简单案例：3NF 关注“传递依赖”

原表：

| 学号 | 学生姓名 | 班级号 | 班主任 |
|---|---|---|---|
| S01 | 小明 | B01 | 张老师 |

函数依赖：

```text
学号 → 班级号
班级号 → 班主任
```

于是：

```text
学号 → 班主任
```

这是通过“班级号”间接决定的，叫**传递依赖**。  
所以该表可能满足 2NF，但不满足 3NF。

### 讲解提示

可以用一句话帮助学生记忆：

```text
2NF 解决“只依赖键的一部分”的问题。
3NF 解决“通过中间属性间接依赖”的问题。
```

---

## 3. 为什么满足 BCNF 的模式可能仍然存在数据冗余？

### 简单案例

关系模式：

```text
教师授课表(教师, 课程, 教材)
```

假设业务规则是：

```text
教师和课程共同决定教材
(教师, 课程) → 教材
```

候选键是：

```text
(教师, 课程)
```

这个函数依赖的决定因素是候选键，所以它满足 BCNF。

但是如果同一门课程通常使用同一本教材，例如：

| 教师 | 课程 | 教材 |
|---|---|---|
| 王老师 | 数据库 | 《数据库基础》 |
| 李老师 | 数据库 | 《数据库基础》 |
| 张老师 | 数据库 | 《数据库基础》 |

虽然满足 BCNF，但“《数据库基础》”仍然重复出现多次。  
这是因为 BCNF 主要处理函数依赖导致的异常，但现实中的冗余可能来自业务习惯、统计信息、历史记录或多值依赖等。

### 讲解提示

可以告诉学生：

```text
BCNF 很强，但不是“消灭所有重复”的万能工具。
数据库设计还要考虑实际业务、查询效率和其他类型依赖。
```

---

## 4. 无损连接性和保持函数依赖不能同时满足时，优先保证哪个？

### 简单案例

假设原表：

```text
学生选课表(学生, 课程, 教师)
```

如果分解后重新连接，会产生原来没有的“学生-课程-教师”组合，那就会造成严重错误。

例如原来只有：

| 学生 | 课程 | 教师 |
|---|---|---|
| 小明 | 数据库 | 王老师 |

但连接后变成：

| 学生 | 课程 | 教师 |
|---|---|---|
| 小明 | 数据库 | 王老师 |
| 小明 | 数据库 | 李老师 |

这会让系统误以为小明也上了李老师的课。

### 讲解提示

通常优先保证：

```text
无损连接性
```

因为无损连接性关系到数据是否真实。  
如果不能保持某些函数依赖，还可以通过程序、触发器、约束检查等方式补救。  
但如果分解是有损的，数据本身就被错误重构了。

# 二、范式判断与分解讲解案例

## 题目背景简化版

作业中的订单表是：

```text
订单表(OID, PID, CID, CName, PName, Qty, WID, WAddr, DDate)
```

可以先用生活化说法解释：

```text
一个订单 OID 可以买多个产品 PID。
一个订单只属于一个客户 CID。
一个产品 PID 有一个产品名 PName。
一个客户 CID 有一个客户名 CName。
一个仓库 WID 有一个仓库地址 WAddr。
```

---

## 二(1) 列出所有非平凡函数依赖

### 简单讲解案例

假设有一条记录：

| OID | PID | CID | CName | PName | Qty | WID | WAddr | DDate |
|---|---|---|---|---|---|---|---|---|
| O01 | P01 | C01 | 张三 | 苹果 | 10 | W01 | 昆明仓 | 2026-06-01 |

可以引导学生这样想：

### 直接依赖

```text
(OID, PID) → Qty, DDate, CID, WID
OID → CID
OID → DDate
CID → CName
PID → PName
WID → WAddr
```

### 隐含依赖

因为：

```text
OID → CID
CID → CName
```

所以：

```text
OID → CName
```

因为：

```text
(OID, PID) → WID
WID → WAddr
```

所以：

```text
(OID, PID) → WAddr
```

因为：

```text
(OID, PID) → CID
CID → CName
```

所以：

```text
(OID, PID) → CName
```

因为：

```text
PID → PName
```

所以：

```text
(OID, PID) → PName
```

### 课堂提醒

学生不一定要机械列出所有通过传递性无限扩展的依赖，但要能说明重要的隐含依赖。

---

## 二(2) 找出所有候选键

### 简单讲解案例

问学生：只知道 OID 可以吗？

```text
OID → CID, CName, DDate
```

但是 OID 不能决定：

```text
PID, PName, Qty, WID, WAddr
```

所以 OID 不是键。

再问：只知道 PID 可以吗？

```text
PID → PName
```

但是 PID 不能决定订单、客户、数量、仓库等信息。  
所以 PID 也不是键。

再看：

```text
(OID, PID)+
```

可以推出：

```text
OID, PID, Qty, DDate, CID, WID, CName, PName, WAddr
```

已经包含所有属性，所以：

```text
(OID, PID)
```

是候选键。

### 讲解提示

可以让学生写闭包：

```text
(OID, PID)+ = {OID, PID, Qty, DDate, CID, WID, CName, PName, WAddr}
```

结论：

```text
候选键是 (OID, PID)
```

---

## 二(3) 判断最高满足第几范式

### 简单讲解案例

候选键是：

```text
(OID, PID)
```

但是存在：

```text
OID → CID
OID → DDate
PID → PName
```

OID 和 PID 都只是候选键的一部分，却可以决定非主属性。

这就是：

```text
部分依赖
```

所以不满足 2NF。

### 结论示范

```text
该关系模式最高满足 1NF。
原因是存在非主属性对候选键的部分依赖，例如 OID → CID、OID → DDate、PID → PName。
```

---

## 二(4) 分解为满足 3NF 且保持函数依赖的模式集合

### 简单讲解案例

可以按照“谁决定谁”来拆表。

### 原来混在一起的问题

订单信息、客户信息、产品信息、仓库信息、订单明细信息全部放在一个表里，导致大量重复。

例如同一个客户 C01 买了很多次东西，CName 会重复出现很多次。

### 推荐分解

```text
订单表 Order(OID, CID, DDate)
主键：OID
保存：OID → CID, DDate
```

```text
订单明细表 OrderItem(OID, PID, Qty, WID)
主键：(OID, PID)
保存：(OID, PID) → Qty, WID
```

```text
客户表 Customer(CID, CName)
主键：CID
保存：CID → CName
```

```text
产品表 Product(PID, PName)
主键：PID
保存：PID → PName
```

```text
仓库表 Warehouse(WID, WAddr)
主键：WID
保存：WID → WAddr
```

### 讲解提示

让学生注意：  
每个表都围绕一个主题，减少重复。

```text
客户姓名只放在客户表。
产品名称只放在产品表。
仓库地址只放在仓库表。
订单日期和客户号放在订单表。
数量和仓库号放在订单明细表。
```

---

## 二(5) 验证分解是否满足无损连接性

### 简单讲解案例

先看：

```text
Order(OID, CID, DDate)
OrderItem(OID, PID, Qty, WID)
```

它们的公共属性是：

```text
OID
```

在 Order 表中：

```text
OID 是主键
```

所以 Order 和 OrderItem 连接时，不会把订单乱配。

再看：

```text
Order 和 Customer 通过 CID 连接
```

CID 是 Customer 的主键，所以不会把客户姓名乱配。

```text
OrderItem 和 Product 通过 PID 连接
```

PID 是 Product 的主键，所以不会把产品名乱配。

```text
OrderItem 和 Warehouse 通过 WID 连接
```

WID 是 Warehouse 的主键，所以不会把仓库地址乱配。

### 结论示范

```text
该分解满足无损连接性。因为每次连接时，公共属性都包含其中一个关系的候选键，可以避免产生寄生元组。
```

---

## 二(6) 进一步提升为 BCNF，并说明是否需要放弃保持依赖

### 简单讲解案例

看分解后的表：

```text
Order(OID, CID, DDate)
```

依赖：

```text
OID → CID, DDate
```

OID 是主键，所以满足 BCNF。

```text
Customer(CID, CName)
```

依赖：

```text
CID → CName
```

CID 是主键，所以满足 BCNF。

```text
Product(PID, PName)
```

PID 是主键，所以满足 BCNF。

```text
Warehouse(WID, WAddr)
```

WID 是主键，所以满足 BCNF。

```text
OrderItem(OID, PID, Qty, WID)
```

主要依赖：

```text
(OID, PID) → Qty, WID
```

(OID, PID) 是主键，所以也满足 BCNF。

### 讲解提示

这个题中，按照上述分解后，基本可以同时满足：

```text
3NF
BCNF
无损连接
保持主要函数依赖
```

但课堂上可以补充说明：

```text
并不是所有关系模式都能同时做到 BCNF 和保持依赖。
有些情况下，为了达到 BCNF，可能需要放弃部分依赖保持。
```

# 三、综合设计题讲解案例

## 题目背景简化版

作业中的考试记录表是：

```text
考试记录表(SID, SName, CID, CName, EDate, Score, GID, GName)
```

可以先解释成：

```text
学生 SID 有姓名 SName。
课程 CID 有课程名 CName。
教师 GID 有教师名 GName。
一个学生在某门课某天考试，会有一个成绩 Score 和一个批改教师 GID。
```

---

## 三(1) 写出所有非平凡函数依赖

### 简单讲解案例

直接给出的依赖：

```text
SID → SName
CID → CName
GID → GName
(SID, CID, EDate) → Score, GID
```

隐含依赖：

因为：

```text
(SID, CID, EDate) → GID
GID → GName
```

所以：

```text
(SID, CID, EDate) → GName
```

因为：

```text
SID → SName
CID → CName
```

所以：

```text
(SID, CID, EDate) → SName, CName
```

因此可以合并写成：

```text
(SID, CID, EDate) → Score, GID, GName, SName, CName
```

### 讲解提示

让学生知道：

```text
隐含依赖不是凭空想出来的，而是通过已有依赖推理出来的。
```

---

## 三(2) 找出所有候选键

### 简单讲解案例

尝试求闭包：

```text
(SID, CID, EDate)+
```

根据题目依赖：

```text
(SID, CID, EDate) → Score, GID
```

再由：

```text
SID → SName
CID → CName
GID → GName
```

所以：

```text
(SID, CID, EDate)+
= {SID, CID, EDate, Score, GID, SName, CName, GName}
```

已经包含所有属性。

所以候选键是：

```text
(SID, CID, EDate)
```

### 讲解提示

可以问学生：

```text
只用 SID 可以吗？不可以，只知道学生不知道是哪门课哪次考试。
只用 CID 可以吗？不可以，只知道课程不知道哪个学生。
只用 SID 和 CID 可以吗？也不一定，因为同一门课可能有多次考试。
所以需要 SID + CID + EDate。
```

---

## 三(3) 判断该模式属于第几范式，并指出问题

### 简单讲解案例

候选键是：

```text
(SID, CID, EDate)
```

但是存在：

```text
SID → SName
CID → CName
```

SID 和 CID 都只是复合键的一部分，却能决定非主属性。

这说明存在：

```text
部分依赖
```

所以不满足 2NF，最高只满足 1NF。

### 存在的问题

#### 1. 数据冗余

同一个学生参加多门考试时，学生姓名会重复出现。

| SID | SName | CID | CName | EDate | Score |
|---|---|---|---|---|---|
| S01 | 小明 | C01 | 数据库 | 2026-06-01 | 90 |
| S01 | 小明 | C02 | 高数 | 2026-06-03 | 85 |

“小明”重复存储。

#### 2. 更新异常

如果小明改名，所有考试记录中的 SName 都要改。  
如果漏改一条，就会产生不一致。

#### 3. 插入异常

新开一门课程，但还没有考试记录时，无法单独插入课程信息。

#### 4. 删除异常

如果删除某课程最后一条考试记录，课程信息也可能被一起删掉。

---

## 三(4) 给出满足 3NF、无损连接且保持依赖的分解方案

### 推荐分解

```text
学生表 Student(SID, SName)
主键：SID
保存：SID → SName
```

```text
课程表 Course(CID, CName)
主键：CID
保存：CID → CName
```

```text
教师表 Teacher(GID, GName)
主键：GID
保存：GID → GName
```

```text
考试记录表 ExamRecord(SID, CID, EDate, Score, GID)
主键：(SID, CID, EDate)
保存：(SID, CID, EDate) → Score, GID
```

### 如何避免插入异常

分解前，如果新开设一门课程，但还没有学生考试，课程信息无法单独存储。

分解后，可以直接插入：

```text
Course(CID, CName)
```

例如：

| CID | CName |
|---|---|
| C99 | 人工智能导论 |

即使还没有任何学生考试记录，也可以保存课程信息。

### 讲解提示

可以让学生总结：

```text
学生信息独立存。
课程信息独立存。
教师信息独立存。
考试成绩和批改教师放在考试记录表中。
```

这样可以减少冗余，并避免插入、删除、更新异常。

# 附加挑战题讲解案例：4NF 和多值依赖

## 简单背景

4NF 主要处理：

```text
多值依赖
```

它和函数依赖不同。

函数依赖是：

```text
一个属性决定另一个属性
```

例如：

```text
学号 → 姓名
```

多值依赖更像是：

```text
一个属性可以独立对应多组值
```

---

## 简单案例

关系模式：

```text
学生信息(学生, 兴趣, 语言)
```

假设：

一个学生可以有多个兴趣，也可以会多种语言。  
兴趣和语言之间没有直接关系。

例如小明：

```text
兴趣：篮球、绘画
语言：英语、日语
```

如果放在一张表中，就必须写成：

| 学生 | 兴趣 | 语言 |
|---|---|---|
| 小明 | 篮球 | 英语 |
| 小明 | 篮球 | 日语 |
| 小明 | 绘画 | 英语 |
| 小明 | 绘画 | 日语 |

这里出现了大量组合冗余。

可以表示为多值依赖：

```text
学生 →→ 兴趣
学生 →→ 语言
```

如果“学生”不是超键，那么不满足 4NF。

---

## 分解方法

应该分解为：

```text
学生兴趣(学生, 兴趣)
```

和：

```text
学生语言(学生, 语言)
```

例如：

**学生兴趣表**

| 学生 | 兴趣 |
|---|---|
| 小明 | 篮球 |
| 小明 | 绘画 |

**学生语言表**

| 学生 | 语言 |
|---|---|
| 小明 | 英语 |
| 小明 | 日语 |

这样就不用保存所有笛卡尔组合。

---

## 分解后是否满足 BCNF？

如果分解后的两个表中没有非平凡函数依赖，或者所有非平凡函数依赖的决定因素都是候选键，那么它们满足 BCNF。

通常这个例子中：

```text
学生兴趣(学生, 兴趣)
学生语言(学生, 语言)
```

没有明显的非平凡函数依赖，因此可以认为满足 BCNF。

### 讲解提示

可以提醒学生：

```text
BCNF 主要看函数依赖。
4NF 进一步看多值依赖。
所以满足 BCNF 不一定满足 4NF。
```

---

# 课堂最后总结

## 学生最容易混淆的地方

### 1. 候选键不是随便选一个编号

候选键必须能推出所有属性。

### 2. 2NF 和 3NF 的区别

```text
2NF：消除部分依赖。
3NF：消除传递依赖。
```

### 3. BCNF 比 3NF 更严格

```text
BCNF 要求每个非平凡函数依赖的决定因素都是超键。
```

### 4. 无损连接比保持依赖更基础

```text
无损连接保证数据连接回来不出错。
保持依赖保证约束检查方便。
```

### 5. 4NF 是处理多值依赖

```text
多个互相独立的多值事实不要硬塞进一张表。
```
